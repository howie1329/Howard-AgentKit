# AgentKit CLI Agent Guide

## Purpose

AgentKit CLI is a small scaffolding tool for installing AI-agent-ready repository guidance into other projects.

This repository owns the npm package `thomas-agentkit` and the CLI command `agentkit`. Keep the project simple, inspectable, and safe by default.

## Project Map

- CLI source: `src/cli.ts`
- Built CLI: `dist/cli.js`
- Bundled install files: `templates/**`
- Bundled Agent Skill: `templates/skills/agentkit/**`
- Installed project guide template: `templates/AGENTS.md`
- Tests: `test/agentkit.test.ts`
- Internal planning docs: `docs/**`
- Skills path docs: `docs/prd-agentkit-skills-path.md`, `docs/agentkit-skills-path-implementation.md`, `docs/agentkit-skill-authoring.md`

The root `AGENTS.md` is for agents working on this repository. `templates/AGENTS.md` is user-facing guidance copied into target projects.

## Guidelines

- Act like a high-performing senior engineer. Be concise, direct, decisive, and execution-focused.
- Solve problems with simple, maintainable, production-friendly solutions.
- Prefer low-complexity code that is easy to read, debug, and modify.
- Choose the smallest path that fully satisfies the requirement.
- Keep command behavior explicit and easy to test.
- Avoid cleverness unless it clearly improves the outcome.
- Treat user edits as intentional. Do not overwrite or revert work you did not make.

## Do Not

- Do not add framework-specific guidance to the root guide unless this CLI repo actually uses that framework.
- Do not add broad abstractions while the CLI remains small.
- Do not introduce new dependencies without a clear production benefit.
- Do not change bundled template paths, CLI output, or install semantics without updating tests and docs.
- Do not conflate CLI `agentkit init` (template install) with skill `agentkit init` (guidance file creation) in docs or CLI help text.
- Do not change package publishing behavior without checking `package.json`.
- Do not run destructive git commands unless explicitly asked.

## Maintainability

Keep the CLI direct and easy to inspect. `src/cli.ts` can stay compact while behavior is simple.

Split code into modules only when new feature complexity makes the single-file CLI harder to understand or test. Good reasons include template personalization, selection logic, or richer preview behavior. Do not split files as a standalone cleanup.

Preserve skip-by-default install behavior unless the task explicitly changes overwrite semantics.

## Before Coding

Before making meaningful code changes:

1. Check whether the task is linked to a Linear issue.
2. If no Linear issue exists, ask whether one should be created before implementation.
3. Create or switch to an appropriate branch:
   - Prefer the branch generated by Linear when available.
   - Otherwise create a clear branch name, such as `feature/template-personalization` or `fix/dry-run-output`.
4. Read the relevant existing code and tests first.
5. For skills-path work, read `docs/agentkit-skills-path-implementation.md` and the PRD naming contract in `docs/prd-agentkit-skills-path.md`.
6. Identify the smallest complete solution.
7. Check whether the change affects CLI behavior, template content, package metadata, or publishing.
8. If the change touches `templates/**`, confirm whether it should affect newly initialized projects only.
9. If the change touches command behavior, update `test/agentkit.test.ts`.
10. If the change touches documented usage, update `README.md`.
11. For larger work, use `docs/agentkit-cli-roadmap.md` or add a short implementation brief under `docs/`.

Tiny docs-only fixes do not need branch or brief ceremony.

## During Coding

- Keep the Linear issue status accurate when work starts, pauses, or materially changes scope.
- Reference the Linear issue in branch names, commits, and PRs when one exists.
- Keep diffs small and reviewable.
- Prefer existing Node.js APIs and current dependencies before adding packages.
- Keep error messages actionable and stable enough to test.
- Validate CLI inputs at the command boundary.
- Preserve dry-run behavior: it must report planned changes without writing files.
- Preserve force behavior: existing files are skipped unless `--force` is used.
- Keep preset behavior explicit: presets may add `STACK.md` and reference it from installed `AGENTS.md`.
- Avoid unrelated formatting churn.

## Templates

Templates are product surface area. Treat them as carefully as code.

- Keep template language generic enough to work across target repositories.
- Do not put this repo's internal workflow into installed templates unless it is generally useful.
- Keep placeholder text intentional and easy for users to replace.
- When adding or removing template files, update the expected template list in tests.
- When changing `templates/AGENTS.md`, remember it is copied into user projects and may be modified by preset logic.
- `templates/skills/` is product surface (like `templates/AGENTS.md`). Skill file changes need test updates and `skills-ref validate` when CI is wired.

## Package And Release Notes

The package is published as `thomas-agentkit`; the installed binary is `agentkit`.

`package.json` uses a `files` whitelist. Published package contents should remain limited to:

- `dist`
- `templates`
- `README.md`

Do not add `docs/**`, local test fixtures, or internal planning files to the published package unless explicitly intended.

Before release-related work, confirm:

- `npm run build` succeeds.
- `npm test` succeeds.
- `README.md` matches actual CLI behavior.
- `dist/cli.js` is current.
- `package.json` metadata and package contents are intentional.

## Project Commands

| Command | Description |
| --- | --- |
| `npm run dev -- init ./tmp-demo --dry-run` | Run the TypeScript CLI locally without writing files |
| `npm run build` | Compile `src/cli.ts` to `dist/cli.js` |
| `npm test` | Build and run the Vitest CLI test suite |
| `npm run prepack` | Run the build step used before packaging |

## Stack

- Node.js >= 18
- TypeScript with ES modules
- Commander for CLI command wiring
- Clack prompts for interactive prompts
- Vitest for tests

## Before Finishing

Before marking work complete:

1. Re-read the original task and confirm the requested scope is satisfied.
2. Confirm any linked Linear acceptance criteria are satisfied.
3. Review the diff for unrelated changes.
4. Run the narrowest useful check:
   - Docs-only changes may skip code checks.
   - TypeScript changes should run `npm run build`.
   - CLI behavior, template, preset, or package metadata changes should run `npm test`.
   - Publishing changes should run `npm run prepack`.
5. Update the Linear issue with implementation notes, checks run, known risks, and follow-up work if one exists.
6. Mention files or areas changed, checks run, known risks, and follow-up work if any.
